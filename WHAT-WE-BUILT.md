# What We Built: ProsHarness

## 1. What this is

You hold a Claude Code subscription and a Codex subscription, and you glue them together by hand. Every step is manual, and the knowledge of *how* you work dies with each session. Claude and Codex can't plan together. You can't control multiple sessions at once. Intermediate output floods your terminal and wastes tokens. Nothing adversarially reviews a plan before you commit real work to it. Each session type wants a different `CLAUDE.md`, but there's only one. You don't want to hunt for skills — you want ranked suggestions. And you want to *learn* from each change, not read jargon about it.

ProsHarness is the system built to close that gap. The outcome: a trigger produces a finding; the finding becomes a plan that Claude and Codex have already argued over; you approve it in a browser (or from your phone); an implementation session opens a draft PR in an isolated worktree; you review it with a timeline of what actually happened, built from recorded fact rather than a guess; the system learns how you work and proposes reusable loops back to you.

There are exactly two points where a human is required: **approving a plan**, and **reviewing a PR before it merges**. The system never merges anything itself.

It was built over seven milestones (M1–M7), plus a cleanup pass and a credential-simplification rework, working from a single plan document (`/home/manas/.claude/plans/so-analyse-this-diagram-shimmering-haven.md`) whose every architectural claim was either measured against the real CLIs or survived four adversarial review rounds with Codex, which opened at RETHINK with three blockers and closed at BUILD REDUCED — three of those objections found real bugs in the design before a line of code existed.

## 2. The three facts everything rests on

These are not assumptions. Each was established empirically, in M0, by driving the real CLIs and reading their output.

**Only the official CLIs spend the subscription.** A headless `claude -p` run's first line of output is a `rate_limit_event`: `{"rate_limit_info":{"rateLimitType":"seven_day","utilization":0.84,...}}` — direct evidence of the real weekly quota being drawn down. Third-party harnesses that looked like alternatives — prime-agent and OMP (`oh-my-pi`, a sibling fork of the same `pi` upstream prime is built on) — don't use that pool at all: both take the subscription's OAuth token and replay it directly against `api.anthropic.com`, spoofing a client fingerprint (deliberately matching headers like `x-app: cli` and a "cowork" beta profile so Anthropic's backend accepts it) and billing per token from "extra usage" by prime's own documentation. This single `rate_limit_event` measurement is what closed that question: the only way to spend the subscription honestly is to shell out to the real CLI as a subprocess, never to fork or re-implement its client.

**A run waiting on a human must own no live process — and a returning MCP tool does not end a turn.** The MCP spec tells clients to enforce a timeout regardless of progress pings, so parking a live agent process on a human decision that might take twenty minutes invites the client to kill it outright. The fix is to checkpoint and resume rather than block. But the non-obvious part — caught by Codex during plan review, and credited explicitly as a catch that "would have cost a week" if missed — is subtler: when an MCP tool call *returns*, the model doesn't stop; it consumes the result and keeps writing. So a tool like `ask_human` can never return success while still expecting the agent to sit still. The design that follows from this: `ask_human` and `submit_plan` durably record the request, and the orchestrator freezes and kills the entire process tree *with the tool call still in flight* — the attempt dies mid-call rather than being allowed to observe a response and act on it.

**`--resume` does not restore the working directory.** Measured directly: a session was started in `dirA` (containing a marker file reading `MARKER_A`), then resumed by pointing the CLI at `dirB` (containing `MARKER_B`). The resumed session reported its `pwd` as `dirB` and correctly read `MARKER_B` off disk — but its conversation memory still described `dirA`. Documented as "the most important thing M0 found, because it is a silent-corruption trap": a run resumed in the wrong tree will edit the wrong files while confidently believing, and reporting, that it's still working in the tree it remembers. Every resume in ProsHarness therefore sets cwd from a durably recorded manifest and is instructed to reconcile against disk before writing anything.

## 3. Architecture

### The pipeline and the two gates

The run state machine, in outline:

```
queued → finding → finding_done → planning → debating → plan_ready
       → awaiting_approval  [GATE 1 — checkpoint, no live process]
       → approved → implementing → verifying (background session)
       → reviewing (Codex adversarial + a fresh ultrareview pass)
       → pr_open → awaiting_review  [GATE 2 — checkpoint, no live process]
       → done | abandoned
```

Any state can also branch to `awaiting_answer` (a plain `ask_human` question, resumed after an answer) or to `failed`. There are exactly two checkpoint states that matter for human judgment — `awaiting_approval` and `awaiting_review` — plus the narrower `awaiting_answer` for point questions. All three share the same defining property: the run owns no live process and holds a durable resume token instead.

**Gate 1 (plan approval)**: a finding produces a plan draft; Codex, working independently from the same finding (not from Claude's draft — deliberately, so its first opinion is genuinely independent), critiques it; Claude revises or defends against structured objections (`severity: blocker|major|minor`); Codex re-attacks only what's still unresolved; this runs for up to two rounds before converging or hitting the round cap. The plan and its objections are written to disk, and the run parks. You see the plan as readable prose, the objections as severity-tagged cards, and you approve, amend, or reject.

**Gate 2 (PR review)**: once approved, a Sonnet-driven implementation session works inside an isolated git worktree, commits, and hands off to a *separate* verification session — never the one that wrote the code — which returns a verdict, not a stack trace. If verification passes, an adversarial review runs: Codex plus a fresh `claude ultrareview` self-review pass, both constrained to the same objection schema Gate 1 uses. Any blocker from either pass stops the pipeline before a PR is even opened. If it clears, a draft PR is opened, and the run parks for you to review and merge yourself.

### Load-bearing design choices

**Journal-as-authority, SQLite as a rebuildable index.** The run's actual source of truth lives on disk, outside any database: `~/.pros/runs/<run_id>/manifest.json` (worktree path, branch, base SHA, diff hash, fence epoch), `journal.ndjson` (an append-only record of every state transition, question, answer, and lease), and per-attempt `raw.log` files holding verbatim CLI output. SQLite is described explicitly as "a rebuildable index over that journal, nothing more" — an earlier version of the design said "rebuild the DB from `raw_events`," which was circular, since `raw_events` lived inside the DB being rebuilt. The reasoning: git and `gh` genuinely cannot reconstruct question/answer ordering, approved plan versions, execution fence epochs, or malformed raw lines — only the journal can. Writing discipline matches the stakes: one serialized writer per run, length-prefixed checksummed records so a torn tail is detectable, fsync on the record and then the directory, atomic temp-write-and-rename for the manifest. A rebuild replays the journal and stops at the first bad checksum, reporting the truncation rather than quietly accepting a short history.

**cgroup containment.** The checkpoint invariant — a parked run owns no live process — needs teeth. A plain POSIX process group isn't enough, because a child can call `setsid` and escape it. So every attempt runs inside a Linux cgroup v2 scope, launched via `systemd-run --scope`, from which no descendant can leave. This is an explicit Linux-only trade-off: portability was judged worth less than a containment guarantee that actually holds.

**The Guardian**, and fail-closed heartbeats. If the orchestrating daemon died before killing a live attempt, a journaled checkpoint would stop nothing — the agent just keeps running and writing. So each attempt runs under a Guardian: the cgroup boundary plus a heartbeat, monitored by a detached watchdog that freezes and kills the attempt if heartbeats go stale. This is belt-and-suspenders against daemon death specifically, independent of the daemon's own liveness.

**The checkpoint sequence** that ties `ask_human`/`submit_plan` to containment, in order: (1) durably append the checkpoint intent with an fsync; (2) freeze the containment boundary before any tool response reaches the model — the attempt dies with the call still in flight; (3) confirm the boundary is actually empty and output file descriptors are at EOF; (4) snapshot `HEAD`, base SHA, and a full working-state hash (staged, unstaged, *and* untracked — a plain `git diff` misses untracked files) into the manifest, fsync; (5) only then append `parked`.

**Fence epochs.** A lease alone isn't enough — after expiry, two recovery workers can both believe they own a worktree. Every state transition, MCP call, verification result, and PR operation carries the run's current fence epoch, and anything carrying a stale one is rejected outright. The epoch bumps on amendment, on recovery, and on lease takeover. Every verdict is bound to `(worktree_sha, plan_version_id, fence_epoch)` specifically so a correct verdict produced before a plan amendment can never be used to approve a tree that has since changed underneath it.

**Orchestrator-allocated worktrees.** The orchestrator allocates the worktree, branch, and lease atomically *before* the agent starts, and hands the path in — the agent owns the contents, never the lifecycle. This was a direct correction of an earlier design (agent-owned lifecycle) after Codex's plan review found a real race: an agent could create a worktree and die before registering it (a false orphan), or delete it after pushing but before completion was recorded (destroying its own manifest). `pros reconcile` is the authoritative reaper, ported from the pattern used by `vibe-kanban`'s `cleanup_orphan_workspaces()` — it scans the workspace directory against the registry and recovers or reports anything inconsistent; automated cleanup never runs before reconcile is clean.

**Model routing.** Findings are driven by Claude at the top tier, with Haiku subagents for search and Sonnet subagents for synthesis. Planning is top-tier judgment work. Critique is Codex, run at high effort, deliberately kept as a genuinely independent first opinion. Implementation runs on Sonnet, dispatched through `scoped-fixer` subagents restricted to an explicit file allowlist. Verification runs on Sonnet in a background session. Review is Codex plus a `claude ultrareview` pass. The framing throughout: cost control is routing plus a concurrency lease, not scope reduction.

**Verification never runs in the session that wrote the code.** Tests, lint, type-checks, review, and diagram generation all run in dispatched background sessions or fresh subagents, and only a verdict comes back — pass/fail plus minimal failing evidence, never a raw stack trace flooding the context that's trying to act on it. `verify.ts` is described in its own milestone log as "the most safety-critical file in the milestone" for exactly this reason: it never resumes the implementer's session, and it checks the fence epoch both before spending any tokens and again after, so a late amendment can't have its verdict silently accepted.

## 4. Every feature, by milestone

**M1 — The checkpoint barrier.** The foundation everything else sits on: Guardian (cgroup containment + heartbeat), Journal (append-only, checksummed, now cross-process locked), Manifest (atomic snapshots), Barrier (the actual checkpoint sequence — request, poll, freeze, confirm-empty, snapshot, park), Fence (epoch bump/check), Resume (cwd reconciliation, a `mkdir`-based recovery lease so only one recovery attempt wins), a detached fail-closed Watchdog, the `ask_human` MCP tool, and the `pros answer` CLI. Verified with 11 kill-tests covering escape attempts, crash timing at every durable-write point, stale fences, and racing recovery attempts — all passing.

**M2 — The plan pipeline.** `pros plan`: adapters that spawn and tolerantly parse both CLIs' event streams (built against real captured fixtures from `claude` 2.1.232 and `codex-cli` 0.147.0), a rebuildable SQLite index over the journal, a worktree allocator built as a crash-safe saga (intent → act → confirm, reusing the same journal M1 built rather than a second durability mechanism), and the finding → plan → critique → debate pipeline itself, capped at two debate rounds and a 300,000-token per-run ceiling checked before every model call.

**M3 — Gate 1.** `submit_plan` (structurally identical to `ask_human` — it never resolves with a value the model can act on), a `PostToolUse` hook on `ExitPlanMode` that corroborates but never authorizes a checkpoint (proven by tests where each fires with the other entirely absent), the first dashboard (Runs, Plan, Questions pages), and push notification via ntfy over Tailscale — one curl, no OAuth.

**M4 — Gate 2.** The implement → verify → review → draft-PR pipeline. A concurrency lease and per-run token ceilings (`@pros/lease`) so admission control is real capacity control, not just cheaper routing. An agent taxonomy derived from actual usage data rather than invented: `finder` (children: `investigator`, `verifier`, `ground-truth-checker`, `pr-auditor`) and `implementer` (child: `scoped-fixer`, the dominant real-world pattern). The draft PR / merge boundary is the hardest requirement here and is enforced for real: a fine-grained GitHub token scoped to `contents: read-only` cannot merge, because GitHub's own merge endpoint checks the same `contents` permission that gates `git push` — a 403 from GitHub's servers, not a client-side refusal this code invented. This was tested against a from-scratch local git stub proving both that the improperly-scoped token is rejected *and* that a properly-scoped one really does move `main`, so the rejection is demonstrably a real boundary and not a no-op.

**M5 — Session graph and review.** `@pros/graph` reconstructs what actually happened in a run purely from parsing recorded `raw_events` rows — no LLM involvement anywhere in the package, guaranteed by construction since `spawnClaude`/`spawnCodex` are never imported there. Every node in the graph carries the literal SQL row id it came from, so a human can verify any claim with a direct query. The review page ranks diff hunks by a documented, deterministic scoring formula (size, generated/lockfile penalties, keyword bonuses for auth/payment/migration-shaped code, a bonus when a hunk touches a file implicated in a real verification failure or review objection) and includes a diagram build step that fails outright, non-zero exit, if a diagram cites a symbol absent from the real TypeScript AST.

**M6 — The learning loop.** `@pros/miner` mines the user's real Claude Code history for correction phrases (four calibrated categories: revert, still-broken, no/wrong, i-told-you), builds deterministic session cards, clusters them into recurring workflows gated on a real outcome signal (a `pr-link` event, present in 90 of 362 sessions) and a checkable structural template, and proposes reusable loops — every single one surfaced with `status: "proposed"`, a status nothing in the codebase ever writes any other value to, on a dashboard page independently verified to contain no form, no click handler, no fetch call: nothing can auto-apply a proposal. `new-to-you` flags commands/tools/extensions the user hasn't used before, scoped conservatively to three kinds so it stays a computed fact rather than a guess.

**M7 — Ambient triggers.** Four trigger sources (Linear, Slack, a credential-free repo TODO/FIXME sweep, Granola), routed through the same admission machinery Gate 2 uses (the same concurrency lease pool, the same per-run token ceilings) and — critically — through the *same* finding pipeline as manual runs, not a parallel one, so a trigger-sourced finding gets the same "cites a real, verified file:line" guarantee a manual one does. A small, static, hand-written skillrank catalog (11 entries, deliberately offline) produces weekly ranked skill proposals. A scheduler daemon (`pros schedule start`) drives trigger sweeps, the Gate-1-continuation job, and the weekly skillrank pass.

**Cleanup and the zero-token rework** (below the milestone line, but real work): a genuine bug in the Guardian was found and fixed (see section 6), the Gate 1 → Gate 2 handoff was wired up end to end (previously `runGate2Pipeline` existed and was tested but nothing outside test files ever called it), and every credential this project originally required was replaced with something the user had already authenticated for another legitimate reason.

## 5. How to run it

```bash
pnpm install
pnpm run start      # builds and starts the dashboard on http://127.0.0.1:3000 (loopback only)
```

Nothing else is required to run the system end to end today. `pnpm run pros <args>` runs the CLI directly via `tsx`, no global install (don't put `--` before the args, or they get silently swallowed). `pnpm run seed:demo` / `seed:reset` populate and clear realistic demo data. Full detail, including every environment variable and its graceful-degradation behavior, is in `RUNNING.md`.

The dashboard's current pages: a Linear-style **sessions board** at `/` (every run as a card in its lifecycle column), a **`/new` trigger front door** (pick a repo, describe a finding, launch a real plan run — Manual works end to end today; Sweep/Linear/Slack/Granola show honest "not ready" states rather than pretending), the **Gate 1 plan page** at `/runs/<id>/plan` (plan as prose, objections as severity-tagged cards, Approve/Amend/Reject), and the **Gate 2 review page** at `/runs/<id>/review` (risk-ranked diff hunks, the draft PR link, a focus checklist). A session graph timeline, a loops page, and schedule/skills pages round it out.

## 6. Interesting findings and learnings

### The guardian cgroup bug: the inconsistency was the signal, not the failure rate

A `@pros/barrier` kill-test — the watchdog test proving containment fails closed when the daemon stops heartbeating — flaked repeatedly across milestones, and each time it was diagnosed differently. In M3, under a full concurrent test-suite run, it failed once because "cgroup scope creation took >5s under that load," passed cleanly alone and in the final full run, and was written off as "a known environment-load flake, not a regression." In M7, the same test was re-run in isolation three separate times and **failed all three**, prompting a stronger note than M6's "one pre-existing flake" framing — this one didn't self-heal on retry, and the log speculated the machine's cgroup v2/systemd scheduling latency under load was the root cause.

That inconsistency — sometimes an environment-load story, sometimes failing repeatedly in isolation with no load at all — turned out to be the tell that the "environment flake" explanation was wrong. The cleanup pass root-caused it properly: `Guardian.launch()`'s readiness check declared a systemd scope ready purely from `systemctl show`'s self-reported `ActiveState=active` plus a non-empty `ControlGroup`, without ever confirming that a real process had actually joined that cgroup. Under back-to-back scope creation and teardown — a pattern only the test suite produces, never real usage — a scope could report itself ready after its sole member process had already died, handing back a Guardian that pointed at nothing. A second latent bug sat next to it: the emptiness check only tolerated `ENOENT` for "cgroup gone," not the equally valid `ENODEV`. The fix checks kernel-truth (a live PID actually present in `cgroup.procs`) instead of trusting systemd's self-report, treats `ENODEV` the same as `ENOENT`, and adds a bounded retry as defense in depth. Verified with 65+ consecutive runs during the fix and five full monorepo test runs afterward — zero occurrences. The lesson worth keeping: a flaky test that gets a *different* plausible-sounding explanation each time it's investigated is a bug you haven't found yet, not noise you can average away.

(Separately, M1 also hunted down and fixed a real — but different — race in `Barrier`'s own poller, where a free-running interval and an inline poll call could both observe "someone else is handling this" and return before the actual freeze/kill/snapshot work had finished. That one actually was root-caused correctly the first time, as a same-process logic race rather than a systemd/cgroup issue, and fixed with an in-flight promise map; 50 consecutive isolated runs, zero failures, confirmed it.)

### Tool-sequence mining was killed by a negative result

Before building anything to mine *how* tools get sequenced, the research pass checked whether it would find anything worth building on. Across every project cluster in the real history — 166 sessions in one, 8 in another, 2 in a third — the single most common tool trigram was always `(Bash, Bash, Bash)`, with `cd` dominating first-token bash calls. As the finding put it: "a production-incident session and a homework session are identical at the skeleton level." `subagent_type` was similarly useless — 875 of 1,366 spawns were just `general-purpose`. Tool-sequence mining was dropped entirely on this basis, before a line of implementation code was written for it. That's the useful shape of a negative result: it saved the cost of a feature that intent-level analysis (which *did* discriminate — see below) made unnecessary anyway.

### Corrections beat praise as a learning signal, by a wide margin

Positive sentiment barely exists in real usage: only 26 hits for language like "perfect" / "thanks" / "nailed it" across 10,520 lines of history, several of them false positives — the research finding is explicit: "do not build on it." Corrections are the opposite: roughly 290 lines matching four categories (revert, still-broken, no/wrong, i-told-you), described as "unambiguous ground truth" — a correction asserts something went wrong; repetition only implies value. When the actual miner was built and run against the real extracted history, it found 309 corrections across those same four categories (58 revert, 96 still-broken, 123 no-wrong, 32 i-told-you) — two categories (`revert` and `i-told-you`) landed on the research estimate's exact counts, the other two in the same order of magnitude, decisively clearing the ≥20-corrections acceptance bar by more than 15×. The system's learning signal is corrections, full stop — there's no praise-weighted counterpart in the shipped design.

### A returning MCP tool call does not end a turn

This is the single discovery that reshaped the entire checkpoint barrier design, and it's covered in section 2 above — worth restating here as the thing that, if missed, would have produced a system that looked correct in every test and then raced past a human decision in production the first time a model kept writing after `ask_human` returned.

### Testing with fake sessions hid a real permission gap

The full plan-to-PR pipeline passed every test built against scripted or fake model sessions. The first time it was driven for real outside a pre-approved interactive session, `pros implement`'s headless `claude -p` subprocess turned out to have no permission grant to edit files or commit — by default, a non-interactive subprocess simply doesn't have the same standing permissions an interactive session accumulates. The result: the pipeline reliably stopped at "verify — no commit," every time, in a way no fake-session test could have caught, because the fakes never modeled permission grants at all. It's recorded plainly in `RUNNING.md` as a known operational gap rather than something quietly patched over — a good example of the difference between "the pipeline logic is correct" and "the pipeline actually runs."

### The credential rework: questioning the setup list instead of trimming it

The original design required five separate credential-shaped configs before the system could do anything beyond manual triggers and scoped-token PRs: a fine-grained GitHub PAT (`contents: read-only`, specifically so it *couldn't* merge), plus API keys for Linear, Slack, and Granola, plus an ntfy URL for push notifications. The rework was triggered by a direct question — "why can't we use the person's already existing creds like already configured MCP or already configured github... that should work without need token also" — and the answer collapsed the entire list to zero required setup, via one repeated move: find something the user already authenticated for a legitimate reason, and drive it through a mechanism the system already trusts.

Concretely: Linear, Slack, and Granola signals now go through the same OAuth-connected MCP servers already showing `✔ Connected` in `claude mcp list`, called via a short-lived, schema-constrained `claude -p` subprocess rather than a direct API key. Notifications default to a Slack DM through that same connection instead of ntfy. And GitHub PR creation moved what the doc calls "the merge boundary from the credential to the process": every model subprocess now has `GH_TOKEN`/`GITHUB_TOKEN` unconditionally stripped from its environment (so no agent ever holds a credential capable of pushing or merging), while the orchestrator itself — deterministic TypeScript, never a model — opens the draft PR through the operator's own already-logged-in `gh auth login` session, whose merge client (`AmbientGhClient.mergePr`) throws unconditionally for any input, by construction, with no reachable code path to a real merge call. Where the old scoped-token path relied on GitHub's servers to enforce the boundary, the new default relies on the orchestrator's own code never calling the command that exists to enforce it. The rework is honest about the asymmetry: the zero-token path trusts the orchestrator process in a way the scoped token never had to, and that stops being a rounding error the moment ProsHarness is used to modify its own source — a self-modifying orchestrator can rewrite its own checks by definition, and no cheap mitigation closes that gap. The scoped-token path was kept, not deleted, for exactly that reason. Every one of the original five credentials was demoted to "optional hardening," not removed from the codebase.

### Other real bugs found only by driving the real CLIs

- `systemd-run --scope` never returns while attached — it stays the scope's supervising process for the command's entire lifetime. The original Guardian awaited the spawned process's exit event and hung forever on any long-running attempt. Fixed by polling `systemctl --user show <unit> --property=ActiveState` instead, and by switching the subprocess's stdio from `"pipe"` to `"ignore"` — an unconsumed pipe eventually backpressures and silently wedges the whole thing.
- `node --import tsx` resolves the bare specifier `"tsx"` relative to the *spawned process's* working directory, not the script's own location. Since `ask_human`'s MCP server gets spawned by `claude` with cwd set to the agent's worktree — a fresh temp repo with no `tsx` anywhere in its `node_modules` chain — this failed with `ERR_MODULE_NOT_FOUND` for `tsx` itself, and `claude` reported nothing more informative than `status: "failed"` unless run with `--debug mcp --debug-file`. Fixed by invoking tsx's own binary by absolute path.
- The journal was originally built assuming one writer process per run (a cached sequence counter, one long-lived file handle) — it broke the moment a second OS process (the MCP subprocess) opened its own `Journal` on the same file and computed a conflicting sequence number. Fixed with a cross-process `mkdir`-based lock around every append, with the sequence number always re-derived from disk under that lock.
- A `checkpoint_requested` journal entry can legitimately be written by a different OS process than the one holding the attempt's live in-memory Guardian — the MCP subprocess opens its own `Barrier` instance whose guardian map is empty. Acting on the checkpoint inline, from the same call that recorded it, silently threw inside that subprocess and the promise never resolved — not because containment worked, but because nobody was ever going to act on it. No unit test caught this, because every unit test happened to call both halves against the same `Barrier` instance. Fixed by splitting "durably record the intent" (works from any process) from a separate 20ms poll loop that only acts on checkpoints its own instance actually owns.
- Codex's live event stream and its persisted rollout files (`~/.codex/sessions/`) use two genuinely different JSON schemas — flat events on stdout, a nested `{timestamp, type, payload}` wrapper on disk. The adapters had to handle both.
- Codex requires its global flags to precede the `resume` subcommand; putting `--sandbox` after `resume <id>` exits 2 with "unexpected argument found." A small thing, but exactly the kind of CLI quirk that only shows up by actually invoking the binary.

## 7. Known gaps and what's next

Stated plainly, consolidated from the project status doc and not softened:

- **The skillrank catalog is a small (11-entry), static, hand-written seed list**, deliberately offline for reproducibility. It will never surface a genuinely new or trending skill outside that list.
- **Three of the four trigger sources' real-network fetch paths (Linear, Slack, Granola) are written but have never been exercised against a real account.** They're gated on credentials that were never available during development.
- **The scheduler is a plain Node process you start and supervise yourself** (`pros schedule start`), not a cron job or system service, and has no watchdog of its own — killing it silently stops all ambient triggers, the Gate 1 continuation sweep, and the weekly skillrank pass until you restart it by hand.
- **The two real-CLI acceptance tests (`@pros/mcp`, `@pros/plan`) self-skip rather than fail** if the live `claude` subprocess doesn't respond within a 60-second budget — a skip-count change from run to run is not automatically a regression, but it does mean part of the suite's coverage is load-sensitive by design.
- **Stage B of the learning loop — LLM-generated, Codex-style session-card prose — was never implemented as a live model call.** This was a deliberate privacy decision (the milestone ran unattended, with no consent mechanism for sending personal history content to an LLM API overnight), so only the deterministic Stage A extraction shipped.
- **The correction-mining regexes were hand-calibrated against one real dataset**, and land in the same order of magnitude as the original estimate per category, not a byte-for-byte reproduction of it.
- **"New to you" is scoped to three candidate kinds** (bash verb, tool name, file extension) behind a small, fixed, conservative allowlist — a genuinely novel command outside that allowlist won't be flagged. A deliberate precision-over-recall trade, not an oversight.
- **Code-structure diagrams (call paths, module boundaries) are out of scope entirely**, on the grounds that tree-sitter-derived call graphs are unreliable under dynamic dispatch, DI, and reflection — the session graph (built from recorded events, zero inference) is the only diagram this system actually ships.
- **No cost/dollar-spend dashboard exists**, by design — subscription utilization is the admission-control signal, token counts are the operational metric, and no dollar total is computed anywhere.
- **This is a single-user, dogfood system with no auth layer beyond being reachable only over your own Tailscale network.** Multi-tenancy was explicitly deferred as a later storage-and-auth refactor, not attempted here.
- **The newer dashboard pages (graph, review, loops, schedule, skills) are tested at the data layer plus static source-inspection, not with a rendered React-testing-library pass** — a consistent convention across the later milestones, not a gap unique to any one of them.
- **`pros implement`'s headless subprocess has no default permission grant to edit or commit outside an already-approved interactive session** — a real operational gap noted directly in `RUNNING.md`, not yet closed.
- At the time of writing, `packages/dashboard` and `pnpm-lock.yaml` have uncommitted local changes from concurrent work on the design system; this document does not touch or depend on that in-flight work.

M7 was the last planned milestone. There is no M8 in the roadmap as written — from here it's a matter of choosing new scope deliberately, not discovering that more was silently expected.
